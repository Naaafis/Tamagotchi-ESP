## 2026-10-21 — Claude — T6+T7 (sim window fix)
- Bug: on macOS the sim window stayed black while the title bar kept updating. Cause: `PyGameDisplay` refreshes from displayio's background thread by posting one pygame event and setting a "refresh pending" flag that only the main thread's event handler clears. `run_desktop.py` called `pygame.event.set_blocked(None)` after creating the display, and SDL flushes queued events of a type it blocks, so that first event was lost and no second one was ever posted. Headless screenshots looked fine only because the screenshot path forces `display.refresh()` at exit, so the live refresh path was never exercised.
- Fix (`sim/run_desktop.py` only): `SimDisplay(PyGameDisplay)` with `auto_refresh=False`; the loop calls `display.refresh()` at 30 fps on the main thread, which draws right there. The group is rendered at the native 320×240 into an offscreen surface and scaled to the window by pygame (a 3× displayio group cost 220 ms a frame, native costs 25 ms), and only the areas displayio marks dirty are redrawn, so an idle pet costs about nothing. The game's group is the display's root group, as on the board; no change to `firmware/pet/`.
- Verified: windowed screenshot after A,A shows the pet and both icon rows; the window surface is already drawn 2 s into a run without a forced refresh; dirty-area rendering is pixel-identical to full redraws over a 35-step scripted run (menu, stats page, 20 min time jumps, sleep); 31 tests pass. Pushed to PR #3.

- Board facts worth knowing (CircuitPython 10.3.1, N8R8 build):
  - Floats are single precision (`1.0 + 1e-7 == 1.0`), so `time.monotonic()` loses resolution over an evening. The game clock is built from `supervisor.ticks_ms()` with wrap-safe subtraction instead.
  - `gc.mem_alloc()` / `gc.mem_free()` each take ~210 ms: they walk the whole 8 MB PSRAM heap. Never call them in the loop. (I did, briefly, and chased the resulting stall for a while.)
  - `gc.collect()` is 1-3 ms with little garbage and ~220 ms the first time after boot when it frees the import-time compiler garbage. The game allocates ~2 KB/s. `code.py` collects once after setup and then only after 60 s without a press, at most every 5 min, so a collection never lands mid-play.
  - displayio refresh cost, measured with `auto_refresh` off: full 320×240 214 ms; pet frame flip (128×128) 58 ms; one icon highlight 9 ms; attention icon or bubble 10 ms; sleep/wake theme change ~200 ms; stats page open 215 ms. That is ~3 µs per pixel of compositing in displayio's scaled-TileGrid path; SPI speed is not the limit (24 MHz requested), and an opaque pet palette only shaves 58 → 50 ms. So the idle animation costs the board 58 ms every 0.6 s in the background. If it ever matters, pre-scaled sprite bitmaps (scale-1 TileGrids) are the lever; T10 could draw the art at native size.
  - Refreshes run between Python statements, so most of their cost lands inside the loop's `time.sleep()` and never shows in a frame's own time. The status line now reports the longest wall-clock gap between two frames, which does include them: 78 ms while the pet idles (one frame flip), 226 ms once at boot for the first full-screen draw.

- ESP32 I2S, from `ports/espressif/common-hal/audiobusio/__init__.c`: 3 DMA buffers of 1023 frames, all preloaded inside `play()` (12-13 ms, blocking), then refilled from background callbacks, which wait while displayio refreshes. So a sound longer than the preload stutters if a refresh outlasts the two buffers still queued: ~190 ms at 16 kHz, ~140 ms at 22.05 kHz. The sleep/wake theme change is ~200 ms, the rest are ≤ 60 ms. Sounds render at 16 kHz for that margin. After a sample ends, I2S keeps clocking zeros until the next `play()`/`stop()`.
- Rendering: MicroPython's `list.extend()` and list slice assignment both copy the whole list on every call, so building a 500 ms beep run by run took 488 ms / 1340 ms. Building each note from a block of whole cycles (pitch within 0.3%) repeated with list multiplication takes 4-46 ms per tune, mostly the `array` conversion. All five tunes are rendered once at boot.
